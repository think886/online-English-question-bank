## 一、性能优化

### B-01 · 词形反查是全表扫描

> 🔖 **第 1 次修订新增**

| 项 | 内容 |
|---|---|
| **来源** | `docs/service-layer.md` 3.4 节（词形归一化） |
| **现状** | `WordMapper.selectByExchangeForm` 使用 `CONCAT(exchange, '/') LIKE CONCAT('%:', #{form}, '/%')`。前置通配符 `%` 导致**无法走索引**，每次划词触发一次全表扫描 |
| **当前影响** | 可接受。`word` 表 36884 行，划词由用户主动触发（非高并发） |
| **待补** | ⚠️ **未做性能压测** —— 只有定性判断，没有实测 QPS/耗时数据 |
| **正确的解法** | 在词典**导入阶段**额外生成一张「形式 → 原形」的反向索引表（如 `word_form(form, word_id)`），归一时直接按 `form` 索引查询。**不要去优化这条 SQL**（如加函数索引），那是治标 |
| **触发条件** | 划词 QPS 上升，或 `word` 表显著变大（引入全量词典后可能到几十万行） |
| **优先级** | 低 |

### ~~B-15 · 任何不存在的 URL 都返回 500，而不是 404~~ ✅ 已解决（2026-09-28）

> 🔖 **第 6 次修订新增；第 9 次修订改为已解决**

| 项 | 内容 |
|---|---|
| **原现象** | 访问任何不存在的地址都返回 **500 INTERNAL_ERROR**。实测：`/swagger-ui/`、`/no-such-page`、`/api/no-such-endpoint` 全是 500 |
| **根因** | `NoResourceFoundException` 自带 404 状态，但 `GlobalExceptionHandler` 的 `@ExceptionHandler(Exception.class)` 无条件返回 500，把状态码盖掉了 |
| **⚠️ 修复过程中的一次真实误判（值得记下来）** | 我按 **Spring 6.x** 的印象以为这些异常都继承 `ErrorResponseException`，于是只加了 `@ExceptionHandler(ErrorResponseException.class)`。结果 **405 修好了、404 仍然是 500**。用 `javap` 查 Spring Framework **7.0.9**（Boot 4.1.1 携带的版本）才发现：<br>`NoResourceFoundException extends jakarta.servlet.ServletException implements ErrorResponse` —— **根本不继承 `ErrorResponseException`** |
| **最终方案** | 不再列异常类型（它们没有共同父类，列清单天生脆弱），改成在兜底处理器里用 `if (e instanceof ErrorResponse er)` **统一尊重异常自带的状态码**。不需要维护任何清单 |
| **附带修正** | ① 新增 `ErrorCode.METHOD_NOT_ALLOWED` / `UNSUPPORTED_MEDIA_TYPE`；② 提示语改为中文且不泄漏 Spring 的内部英文消息；③ 4xx 记 debug、5xx 才记 error，日志里的假告警归零 |
| **验证** | 冒烟测试新增 4 项断言（未知页面/未知 API/`/swagger-ui/` → 404，GET 打 POST 接口 → 405），86 → **90 项全通过**；实测日志中「未预期的服务端异常」计数为 **0** |

**第 9 次修订：两项不安全功能收进了一个开关**

原来「调试身份头」是写死在解析链里的、「演示弱口令」是每次启动无条件补设的 ——
要关掉它们得去代码里翻。现在都受 `application.yml` 的 **`app.dev-mode`** 控制：

| `app.dev-mode` | `X-Debug-User-Id` | 补设 `demo123` | 启动日志 |
|---|---|---|---|
| `true`（当前） | ✅ 接受 | ✅ 会补设 | ⚠️ **7 行 WARN 告警**，明说这两项不可用于对外环境 |
| `false` | ❌ **忽略（401）** | ❌ 不补设 | INFO 说明只认 Bearer 令牌 |

代码里的兜底默认值是 `false`（`@Value("${app.dev-mode:false}")`），

**已验证**（2026-09-28）：
- `app.dev-mode=true`：90 项冒烟断言全通过
- `app.dev-mode=false`：`X-Debug-User-Id` → **401**（后门关闭），Bearer 令牌 → **200**（正规路径不受影响）

> ⚠️ **本次实测发现的一个反直觉行为，必须写清楚**：
> 关掉 `app.dev-mode` **不会**让 `demo/demo123` 登录失败 ——
> 密码早已写进 `sys_user`，而配置开关不该去删数据。
> 也就是说 `dev-mode=false` 只阻止**创建**弱口令，不负责**清除**已存在的。
> 所以上线前仍必须**手工删掉 demo 用户或改密**，这一条不能靠开关兜住。

**仍然遗留（按优先级）**：

1. **`app.dev-mode` 默认值必须切成 `false`**，而这一步**被 B-17 卡住** ——
   没有注册接口就没有任何办法拿到令牌，关掉后连本地自测都做不了。
   所以正确顺序是：**先做 B-17，再切默认值**。
2. **删掉 `demo` 用户或改掉它的密码**（见上方反直觉行为说明）。上线前的硬性动作。
3. **`X-Debug-User-Id` 相关的回退代码最终应整体删除**（连同 `tools/api-smoke.ps1` 里

4. **令牌没有到期清理机制** —— 见 B-18。
5. **没有刷新令牌**，令牌一过期就得重新登录（有效期 7 天，暂可接受）。
6. **`AuthService.revokeAll(userId)` 目前没有调用方** —— 改密码接口做出来后必须接上，
   否则改密码不会把别处的登录踢下线。

### B-12 · 错误码不够精确（404 未区分、403 未使用）

> 🔖 **第 4 次修订新增**

| 项 | 内容 |
|---|---|
| **现象 1** | 请求不存在的文章返回 **409 CONFLICT**，而非语义正确的 **404 NOT_FOUND** |
| **现象 2** | 「会话不属于该用户」也返回 409，而非 **403 FORBIDDEN**（第 5 次修订补充：已在 `tools/api-smoke.ps1` 中实测确认，见 `docs/api-layer.md` 9.5） |
| **根因** | 全局异常映射把 `IllegalStateException` 统一映射成 409，无法区分「资源不存在 / 无权访问 / 状态冲突」。而 Service 只抛 `IllegalArgumentException` 与 `IllegalStateException` 两种异常 |
| **影响** | 前端无法做差异化提示（「换一篇文章」vs「无权访问」）；监控告警分不清错误性质 |
| **为什么不立刻修** | 精确区分需要在 Service 层引入能表达「资源不存在 / 无权访问」的异常类型，即引入业务异常体系。第 1 次设计时已论证**不引入**（避免 Service 感知 HTTP 语义），为一个场景破例不划算。等接口补齐、真实前端需求明确后再统一处理更合适 |
| **可选方案** | ① 引入极薄的业务异常（携带错误码，不感知 HTTP）；② Service 返回结果对象而非抛异常；③ 保持现状，仅在需要的接口由 Controller 做前置校验 |
| **触发条件** | 接口补齐后、前端提出差异化错误提示需求时 |
| **参考** | `docs/api-layer.md` 第 9.4 节（实测证据） |
| **优先级** | 中 |

### B-17 · 没有注册接口，也没有改密码接口

> 🔖 **第 7 次修订新增**

| 项 | 内容 |
|---|---|
| **现状** | 登录有了，但**新用户无法自助注册** —— `SysUserService.register()` 只有 Service 方法，没有对应的 HTTP 接口。目前新建用户只能由管理员直接写数据库（`tools/api-smoke.ps1` 就是这么干的：直接 INSERT 再复制 demo 的密码哈希） |
| **影响** | 前端做不出注册页；也无法让用户自己改密码 |
| **改密码还牵出一个安全问题** | 改密码必须**同时撤销该用户的全部既有令牌**（`AuthService.revokeAll`），否则旧密码换掉了、旧令牌还在别处有效。而 `setPassword` 与 `revokeAll` 分属两个 Service，是跨表操作，需要一个专门的应用服务把两者组合进**同一个事务** |
| **要做的事** | ① `POST /api/auth/register`（用户名查重 + 密码强度校验 + BCrypt 入库）<br>② `POST /api/auth/change-password`（校验旧密码 → 改密 → `revokeAll` → 重新签发令牌）<br>③ 密码强度规则（当前只校验非空） |
| **优先级** | 中高（注册是「能给人用」的前提） |

| **依赖** | `B-17`（注册登录页需要注册接口）、`B-20`（CORS） |
| **可分阶段** | 最小可用版只要三页：**做题页（含划词）+ 结果页 + 生词本**。错题本、历史、注册可以后补 |
| **优先级** | **高**（决定了这个项目能不能真的被使用） |

### B-20 · 前端跨域（CORS）与令牌存放位置未定

> 🔖 **第 8 次修订新增**

| 项 | 内容 |
|---|---|
| **现状 1** | 后端**没有配置任何 CORS**。前后端分离后浏览器会拦掉所有请求（`No 'Access-Control-Allow-Origin'`） |
| **现状 2** | 令牌存哪里**尚未讨论**。放 `localStorage` 会扩大 XSS 的影响面（一次 XSS 就能把令牌偷走，且 7 天内都有效）；放 HttpOnly Cookie 则免疫 XSS 但需要处理 CSRF |
| **现状 3** | 若选 Cookie 方案，`POST /api/auth/login` 与 `/logout` 的契约都要改（改为 `Set-Cookie`），且需要加 CSRF 防护 —— 属于**接口契约变更**，越晚定代价越大 |
| **可选解法** | ① 令牌放内存（Pinia/Redux）+ 刷新页面后重新登录（最安全，体验略差）<br>② 放 `localStorage` + 短有效期 + 刷新令牌（常见折中）<br>③ HttpOnly Cookie + CSRF token（最安全，改动最大） |
| **建议** | 在动手写前端**之前**定下来，因为它会反向影响 `AuthController` 的响应形态 |
| **优先级** | 中高（写前端前必须先定） |

### B-18 · 令牌表缺少清理与并发登录控制

> 🔖 **第 7 次修订新增**

| 项 | 内容 |
|---|---|
| **现状 1** | 过期令牌行会**永久留在 `user_token` 表**里。每次登录插一行，长期运行会持续增长 |
| **现状 2** | 同一用户可以无限次登录，产生无限多有效令牌。没有「最多 N 个设备」或「登录时踢掉最旧的」策略 |
| **现状 3** | `last_used_at` 是**节流更新**的（距上次记录超过 5 分钟才写）。这是刻意的性能取舍，但意味着它的精度只有 5 分钟，不能用来做精确的活跃度统计 |
| **可选解法** | ① 登录时顺带 `DELETE FROM user_token WHERE expires_at < NOW() OR revoked_at < NOW() - INTERVAL 7 DAY`（简单，无需定时任务）<br>② 独立定时任务清理<br>③ 登录时按用户统计有效令牌数，超限则撤销最旧的 |
| **为什么不是现在做** | 当前只有开发期数据，量级为个位数；且清理策略需要先定「保留多久」，属于策略决策 |
| **优先级** | 低（上线前做第 ① 条即可） |

### B-14 · 结果页的标记词只保留一个句子快照

> 🔖 **第 5 次修订新增**

| 项 | 内容 |
|---|---|
| **现状** | `MarkedWordSummary` 的 `firstSentence` 只取「文本中最靠前的那次标记」的句子。同一个词若在文中出现 3 次、用户标了 3 次，结果页只能看到其中 1 个语境 |
| **影响** | 复习时看不到该词的其他用法。对「一词多义」的词损失明显 |
| **可选解法** | ① `MarkedWordSummary` 改为带一个句子列表（去重后，限制条数）；② 结果页点开某个词时再单独请求该词的全部标记（`GET /api/me/marks?form=run`） |
| **附带** | 顶层 `markedWords` 刻意不带锚点（`questionId`/`sourceField`）是正确的 —— 同一个词锚点不唯一。但这也意味着「想从某个词跳到原文位置」必须有方案 ② |
| **优先级** | 低（当前每会话标记量小，实际影响有限） |

### B-08 · 数据库密码明文写在 git 跟踪的文件里

> 🔖 **第 1 次修订新增**

- **现状**：`src/main/resources/application.yml` 里的 `spring.datasource.password` 是明文，且该文件**被 git 跟踪**（`.gitignore` 未忽略）
- **风险**：推到公开仓库即泄露
- **解法**：改成 `spring.datasource.password: ${DB_PASSWORD:}`，密码由环境变量提供
- **优先级**：**高**（在任何对外发布之前必须处理）

> 🔖 **第 1 次修订新增**

- **现状**：`application.yml` 里 `logging.level.org.example.englishquestionbank.mapper: debug`，会打印全部 SQL
- **解法**：改成 `info` 或删除该行
- **优先级**：高（上线前）

### B-10 · 开发期自检类需要清理

> 🔖 **第 1 次修订新增；第 5 次修订补充**

- **现状**：`config` 包下有 6 个 `CommandLineRunner` 自检类，每次启动都执行
- **解法**：删除，或加 `@Profile("dev")` 限制只在开发环境生效
- **第 5 次修订补充**：开发期工具现在还包括 `tools/api-smoke.ps1`（接口冒烟测试，
  会临时建测试用户再删除）。它不在应用进程里、不会在启动时执行，
  但发布时也应一并归档或移出交付物
- **清单见** `docs/README.md` 第三节
- **优先级**：中（上线前）

> ⚠️ **写自检类时的注意**（第 5 次修订新增）：
> 自检**不要断言全局绝对值**（「该用户的 `mark_count` 必须是 1」「该用户的错题必须正好 2 条」），
> 那等于假设「除我以外没人写这个用户的数据」，手工测一次就会误报。
> 应该断言**自己造成的增量**，或把查询结果过滤到自己创建的那个 session/用户上。
> 详见 `docs/api-layer.md` 9.7。
